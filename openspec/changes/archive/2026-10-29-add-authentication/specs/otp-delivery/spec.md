# Spec Delta

## Purpose

Issues, delivers and checks one-time codes sent to Indian mobile numbers, for any purpose (login now, onboarding signup next), under one set of abuse and privacy rules.

## ADDED Requirements

### Requirement: Code format and storage

A one-time code SHALL be 6 random digits, valid for 5 minutes, for one phone and one purpose. Codes MUST be stored only as a keyed hash, never in plain text, and MUST NOT appear in logs or API responses (outside the development console sender).

#### Scenario: Stored form

- **WHEN** a code is issued
- **THEN** the database holds a hash of it and not the 6 digits

### Requirement: Verification rules

A code SHALL verify only for the phone and purpose it was issued for, only before it expires, and only once. A new code for the same phone and purpose replaces the previous one. After 5 wrong attempts the code is locked and cannot be verified, even with the right digits.

#### Scenario: Correct code

- **WHEN** the right code is submitted within 5 minutes
- **THEN** verification succeeds and the code cannot be used again

#### Scenario: Expired code

- **WHEN** the right code is submitted after 5 minutes
- **THEN** verification fails

#### Scenario: Lockout

- **WHEN** 5 wrong codes have been submitted
- **THEN** the right code is also rejected until a new code is requested

#### Scenario: Replaced code

- **WHEN** a new code is requested and the older code is submitted
- **THEN** verification fails

### Requirement: Resend limits

A new code for the same phone and purpose SHALL NOT be sent within 30 seconds of the previous one, and at most 5 codes SHALL be sent per phone per hour. Requests inside these limits are refused with `429` code `OTP_COOLDOWN`, telling the client how many seconds to wait.

#### Scenario: Too soon

- **WHEN** a second code is requested 10 seconds after the first
- **THEN** the response is `429` with code `OTP_COOLDOWN` and a retry-after of about 20 seconds

#### Scenario: Hourly cap

- **WHEN** a sixth code is requested within an hour
- **THEN** the response is `429` with code `OTP_COOLDOWN`

### Requirement: Delivery through apitxt

In non-development environments, codes SHALL be delivered by SMS through apitxt. The code is generated by Ninno and sent as the `otp` field, with the number in `91XXXXXXXXXX` form. A delivery failure SHALL be logged with the masked phone and the provider status only, and the client SHALL get `502` code `OTP_DELIVERY_FAILED`.

#### Scenario: Provider accepts

- **WHEN** apitxt answers `{ "status": "success" }`
- **THEN** the code counts as sent

#### Scenario: Provider rejects

- **WHEN** apitxt answers with HTTP 401 `{ "status": "AUTH_FAILED" }`
- **THEN** the client gets `502` with code `OTP_DELIVERY_FAILED`, and the log entry contains no code and no full phone number

### Requirement: Development delivery

In development and test, codes SHALL be delivered to the API log instead of SMS. The API MUST refuse to start in production when configured with the console sender, or with apitxt but without an auth key.

#### Scenario: Console sender in production

- **WHEN** the API starts with `NODE_ENV=production` and `OTP_SENDER=console`
- **THEN** startup fails naming `OTP_SENDER`
